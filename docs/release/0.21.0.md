# minanode 0.21.0 release notes

0.21.0 launches the web node: a Mina devnet full node that runs in a browser
tab. It is at [minaweb.org](https://minaweb.org) and in a downloadable archive.
It is the same Rust node, compiled to WebAssembly. It is a beta release on
devnet only, for desktop Chrome and Chromium only. Use only devnet keys.

## Web node

minaweb.org opens on a start screen. Nothing downloads until you press Start (PR
#253). The node then syncs devnet from its relays and checks the best tip's
proof itself. It then checks the proof of each new block. It shows blocks,
accounts, the transaction pool and its peers. The transaction pool labels a
transaction a block can take now as Ready, and one behind an earlier nonce as
Waits for nonce N (PR #262).

The browser saves the chain the node synced. A reload starts from that copy and
catches up from the relays. The reset on the Start-up page deletes it.

The page runs under a strict Content-Security-Policy, with no inline or
evaluated script, and refuses to be framed (PR #251). It checks the WASM's
SHA-256 before running it. Its links to the docs name the docs page they open
(PR #272).

## Keys and roles

A tab can generate a key or import one, and send payments. It imports a raw
private key or a Mina encrypted key file, the format `mina wallet generate` and
the OCaml node write. The WASM decrypts the file off the page's thread. It
refuses a file that needs more than 256 MiB of memory to decrypt. A held key can
be downloaded as a key file for a native node, under a password of at least 10
characters (PR #263).

The tab holds a key in memory, and saves it encrypted in the browser only on
request. It keeps the key through role changes, with no passphrase (PR #252).
The page refuses a saved key that asks for more than 1,200,000 PBKDF2
iterations. After a role change, it drops a carried key that doesn't derive its
public key. The WASM wipes passwords and key bytes when it drops them. Deleting
the saved copy asks for confirmation first (PR #271).

A tab runs a SNARK worker or a block producer, one role at a time. Changing role
restarts the node. The block producer's start card takes an optional coinbase
receiver, as the native `--coinbase-receiver` does (PR #259).

## Sync

A tab dials every relay its page lists. It times each relay's answers and sends
most of its requests to the nearest one, the staged ledger among them. A farther
relay gets one request at a time and takes over if the nearest one stops (PR
#265).

Requests to a relay are pipelined, five at a time, and time out on silence, not
on slowness. The relay's WebRTC transport no longer throttles itself on a long
path (PR #257).

Near the relays, a fresh sync takes about 50 s (median 51.7 s over five runs),
and a reload with the saved chain about 26 s (median 26.4 s). From the US West
Coast, about 170 ms from the relays, a fresh sync takes about 3 minutes (median
192 s over three runs), and a reload about 90 s. Fresh runs used empty browser
profiles on public devnet. Reloads reused those profiles after the chain was
saved. Timing starts before the page loads from a local server and ends at
Synced, within one block of the highest peer. It excludes browser launch and
downloads from the production CDN. These figures come from two test locations
and are not guarantees.

The relay paces its WebRTC sends and bounds its loss recovery (PR #264). Over a
real path of about 160 ms, browsers reached Synced 20% sooner in eight paired
runs. With 0.5 to 1% random loss added in a lab, the staking-ledger download was
about 7% slower.

A slow bootstrap keeps its staged ledger download when the best tip moves,
instead of starting it again (PR #269). At 160 ms, a bootstrap fetched the parts
once, 37 to 39 MiB, against up to 299 MiB before.

## Sharing with other browsers

Sharing lets other visitors' web nodes sync from yours. It is off by default.
The switch is on the Peers page, and the browser keeps the choice (PR #261).

With sharing on:

- The browsers you connect to see your public IP address.
- It uses your upload: up to about 130 MiB for each tab you help sync, then tens
  of MiB an hour for each connected browser.
- The tab still dials only its relays and asks them for introductions. It
  connects to at most 4 browsers and serves at most 2 bootstraps at once.
- It sends connectivity checks only to another browser's public addresses and
  mDNS names, never to a private address on your network.

The public minaweb.org relays run with `--webrtc-sharing-relay`. Visitors choose
whether to share on the Peers page.

With `--webrtc-sharing-relay`, a relay introduces only browsers that turned
sharing on. Each relay permits at most 6 introductions per peer key per hour, 12
per IPv4 address or IPv6 /64 per hour, and 120 in total per hour.

## Relays and privacy

A browser can't reach OCaml nodes. It reaches the network through relays: native
nodes that browsers can reach over WebRTC. Each tab dials every relay its page
lists, and keeps following the chain while one relay is down (PR #255). At
launch the list is `relay1.minaweb.org` (Falkenstein) and `relay2.minaweb.org`
(Helsinki).

The Peers page shows each relay: connected or not, its route (direct or through
TURN), round trip and data. It shows no addresses (PR #256).

Each relay, its STUN and TURN server, and the hosts the page's files come from
see the visitor's IP address. With sharing on, so do the browsers the tab
connects to. Each relay's TURN server forwards only to that relay.
[How the web node works](https://minanode.org/docs/web-node-connections/)
explains the routes and who sees what.

## Web archive

`mina-web-0.21.0.tar.gz` runs the same node from your own computer. Check it
against the signed `SHA256SUMS`, unpack it and run `python3 -B serve.py`. Open
`http://127.0.0.1:8080/` in desktop Chrome or Chromium. The server checks every
file against the archive's manifest before it listens on `127.0.0.1`.

The archive holds the page, WASM, prover files and genesis configuration. The
node builds its verifier indexes at start. `--relay` replaces the packaged
relays; give it once per relay. The server refuses an IPv6 relay, which a
Content-Security-Policy can't name. The archive has no TURN servers and uses
public STUN servers, Google's among them.
[Run the web node yourself](https://minanode.org/docs/run-web-node/) has the
steps.

## Run a relay

A native node serves browsers with `--webrtc-signal-port`, open WebRTC UDP ports
and HTTPS signalling. minaweb.org dials only its own listed relays. Your relay
serves a web node you run yourself with `--relay`. See
[Run a relay](https://minanode.org/docs/run-a-relay/).

`--webrtc-sharing-relay` makes a relay introduce browsers that turned sharing on
to each other (PR #261). 0.21.0 removes `--webrtc-signaling-relay`. Use
`--webrtc-sharing-relay` instead (PR #268).

The minaweb.org relays run behind nginx, with per-address rate and connection
limits. Their coturn is 4.18.0, built from the pinned upstream release tarball
in place of Ubuntu's 4.6.1. Its TURN credentials expire, and one address gets
one username, so coturn's quota applies per address. The relay, coturn and the
credential service run in systemd sandboxes. Visitor addresses are logged only
in the journal, retained for at most 7 days. nginx startup errors contain no
visitor addresses and are retained separately for 14 days (PRs #266 and #267).

Caddy, which has no built-in rate or connection limits, is for a private relay
only. Its signalling bodies are capped at 128 KiB, as nginx's are (PR #271).

## Known issues

- Only desktop Chrome and Chromium are tested. Other browsers are unsupported.
- Browser tests covered key handling, unfunded-payment rejection, funded
  payments and worker proof offers. Two payments sent back to back went into the
  same block. Worker purchases and staked production from this app are untested.
- Relay capacity is unmeasured.
- Sync over long paths with packet loss is unmeasured on this build.
- If the nearest relay stops while it sends the staged ledger, the download
  starts again from a farther relay, at that relay's speed. In tests, such runs
  took 2 to 17 minutes.
- A relay that is full can drop a browser that is still syncing, to make room.
  The browser then starts its download again.
- While a relay's host is down, its TURN server stays in the tab's list until
  its credentials expire. Each new connection can then take up to 3 s longer.
- The relays offer TURN over UDP and TCP on port 3478, not over TLS on port 443.
  A network that allows only HTTPS can't reach them. With all UDP blocked except
  DNS, a browser synced through TURN over TCP in 73 s.
