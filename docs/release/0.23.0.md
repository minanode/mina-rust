# minanode 0.23.0 release notes

0.23.0 lets a Rust node serve the staged ledger that a bootstrapping peer asks
for, up to 192 MiB. On devnet, that answer was about 172 MB on 2026-11-18, and
no 0.22.2 node could send it to an ordinary libp2p client. Upgrade the nodes
that other nodes bootstrap from. The release also cuts memory in the transaction
pool and in block apply, and adds `--no-serve-retired-staged-ledgers` for nodes
that serve no bootstrapping peers. The dashboard gets an Archive page. One
change affects scripts. `POST /archive/resend` now needs a header and a JSON
body. See [Changed](#changed). 0.23.0 is a beta release. The web node runs on
devnet only. Use only devnet keys in it.

## Rust nodes serve devnet bootstraps

A bootstrapping node asks a peer for the staged ledger of its root: the scan
state, the pending coinbase and the protocol states. A Rust node now sends an
answer of up to 192 MiB over libp2p, RPC framing included ([#60]).

- **The old limit.** 0.22.2 reset the stream when an answer exceeded its 64 MiB
  per-peer queue plus the client's receive window. For an idle server and a
  fresh 256 KiB window, which Rust and OCaml clients open with, that is about 67
  MB. On 2026-11-18, devnet's answer was 172,154,270 bytes. Mainnet's was 64.7
  MB, 2.6 MB under the old limit. Over WebRTC, which the web node uses, 0.22.2
  sent the answer in parts and did not hit this limit.
- **An empty answer instead of a reset.** The node measures the answer before it
  encodes it. An answer over the limit, or one whose measured size the send
  budgets have no room for, gets an empty answer, as for a block the node
  doesn't have. OCaml 4.0.4 and the Rust node then ask another peer. 4.0.4
  lowers no peer's trust for an empty answer.
- **The capacity error.** A request that arrives while the budgets can't hold
  its reservation is refused before any work. It gets the capacity error that
  OCaml's rate limiter sends, as in 0.22.2.
- **Budgets.** One peer may queue up to 192 MiB. 0.22.2 allowed 64 MiB. The
  node-wide budget stays at 256 MiB.
- **One copy of the answer.** The node encodes the answer once, in 1 MiB chunks,
  and frees each chunk once it is sent.

The test ran on a throwaway 8-vCPU VM on 2026-11-18. A node with this change
synced devnet from public peers in 41 s. Each client then ran as its own user,
with only that node as its peer. A firewall blocked those users' traffic that
left the machine.

- A 0.22.2 Rust client synced 41.6 s after launch.
- An OCaml 4.0.4 client finished bootstrap on its first try in 146.6 s. It was
  synced 368 s after launch.
- With four, four and two clients asking at once, one got the answer each time.
  The others got the capacity error.
- In a test the same day with a 0.22.2 server as the only peer over libp2p,
  neither a Rust client nor an OCaml 4.0.4 client synced in 10 minutes. A Rust
  client synced from the same server over WebRTC.

## Less memory for pooled commands and block apply

- **The transaction pool keeps one copy of each command.** 0.22.2 kept a copy
  for each of the pool's indexes. For 120 zkApp commands with 15 real devnet
  proofs each, one per sender, the pool took 37.6 MiB instead of 85.2 MiB with
  proofs in memory. With proofs in files, it took 16.5 MiB instead of 64.1 MiB
  ([#61]).
- **Block apply reads the latest ledger proof without copying transactions.**
  0.22.2 copied the transactions of the last emitted tree each time it read that
  tree's proof. For a tree of 121 zkApp commands with 15 proofs each, one copy
  was 32.4 MiB. In a benchmark of one such block, the heap's peak above its
  starting point fell from 98.3 MiB to 55.1 MiB during apply. During production,
  it fell from 117.6 MiB to 85.2 MiB. In a replay of 15,897 archived mainnet
  blocks, every staged ledger hash matched ([#62]).

These figures come from heap-counting harnesses, not from live nodes.

## Keep no scan states for retired roots

A node keeps the scan states of its last `k + 10` retired roots, 300 on Mesa, as
OCaml does. A bootstrapping peer may ask for a root that the node has already
retired, and these scan states answer it. `--no-serve-retired-staged-ledgers`,
or `MINA_NO_SERVE_RETIRED_STAGED_LEDGERS`, keeps none ([#63]).

- **What a peer gets.** With the flag, the node answers a request for a retired
  root as for an unknown block. The peer asks other peers. OCaml 4.0.4 lowers no
  peer's trust for this answer. If no other peer has the root, an OCaml peer
  starts its bootstrap again.
- **What the node still serves.** The node still serves the staged ledger of
  every root in its frontier, and the blocks of the roots it retired.
- **When to use it.** Use it on a node that no peers bootstrap from. Leave it
  off on a seed, or on any node that peers rely on to bootstrap. The flag is off
  by default, and a node without it keeps and serves what 0.22.2 did.
- **The web node.** By default, it dials only its seed relays and sharing is
  off. In that mode it keeps no retired root scan states. With sharing on, or
  with the experimental unrestricted peering, it keeps them as before.

A replay of 700 full blocks, each with 12 zkApp commands of 15 proofs, into a
frontier of 291 blocks and 300 retired roots measured the saving. The live heap
fell from 9.00 GiB to 6.73 GiB with proofs in memory, a block producer's
default. It fell from 5.93 GiB to 3.77 GiB with proofs in files, the default of
a node that doesn't produce. On a throwaway VM, two devnet nodes synced from
empty work directories, one with the flag. Three blocks later, the default node
served its retired root, and the flagged node gave the answer for an unknown
block.

## The dashboard's Archive page

A node started with `--archive-archiver-process` sends each block it applies to
an OCaml archive process. Its dashboard now has an Archive page. The page shows
whether the feed is up to date. It replays one retained block, or all of them,
to the archive ([#64]).

The page can also check the archive's database. Start the archive with
`--metrics-port`, and set `MINA_ARCHIVE_METRICS_ADDRESS` on the node to the URL
of that port. The node reads the archive's own counts every 60 s and never
connects to PostgreSQL. The page then says whether the database is complete.
There is no new flag.
[The Archive page](https://minanode.org/docs/dashboard/#archive-page) describes
the check, its limits and the ports to block.

A test on a local PostgreSQL 16 and mina-archive 4.0.4, fed by a node following
devnet, gave these results:

- After a block's rows were deleted, the page said Incomplete after 57 to 147 s.
  A replay brought the rows back, and the page said Complete.
- While PostgreSQL was stopped, the archive acknowledged three blocks and
  dropped them. The page said Behind after 6 minutes, then Incomplete with 3
  missing after the restart. Resend all retained filled them.
- With the archive stopped, the page said Unavailable at the next read. It said
  Complete 53 s after the archive restarted.

## Changed

- **`POST /archive/resend` needs a header and a JSON body.** In 0.22.2, a plain
  `curl -X POST` to the route requeued every retained block. In 0.23.0, on a
  node that feeds an archive, a request without the `x-mina-archive-control`
  header gets 403. With the header, a request without
  `content-type: application/json` gets 415, and an empty or invalid JSON body
  gets 400. For a request with no `Origin` header, as `curl` sends it, the 403
  and 415 errors show the full command. From a browser, only pages of this
  machine, the node's own dashboard at an IP address and origins listed with
  `--worker-control-origin` may send it. Pages of other origins get 403 ([#64]).
  A node that feeds no archive answers 404, as in 0.22.2. To requeue every
  retained block:

  ```sh
  curl -X POST http://127.0.0.1:3000/archive/resend \
    -H 'x-mina-archive-control: 1' -H 'content-type: application/json' \
    -d '{"all": true}'
  ```

  To requeue one block, send `{"state_hash": "3N..."}` instead.

- **`DiffResult::ledger_proof` is `Option<LedgerProof>`.** It was a pair. Rust
  code that uses the `mina-tree` crate and reads it must drop the second element
  ([#62]).

## Upgrade from 0.22.2

Replace the binary as the
[install guide](https://minanode.org/docs/install/#upgrading) describes. Start
the node with the same work directory and flags. 0.23.0 needs no state
migration. If a script of yours calls `POST /archive/resend`, add the header and
body shown under [Changed](#changed).

With Docker, pull `ghcr.io/minanode/mina-rust:0.23.0` and check its digest, as
[Docker](https://minanode.org/docs/docker/#stop-and-upgrade) describes.

`mina-web-0.23.0.tar.gz` runs this release's web node from your own computer,
through the minaweb.org relays.
[Run the web node yourself](https://minanode.org/docs/run-web-node/) has the
steps.

## Known issues

- The 192 MiB limit bounds the encoded answer, not the memory used to build it.
  The node converts the whole scan state before it measures the answer. An
  answer over the limit is built in full and then refused.
- Answers over 192 MiB get the empty answer. The largest devnet answer measured,
  173.8 MB, is about 26 MiB under the limit.
- In the devnet test, each answer raised the server's resident memory by about
  330 MiB for half a second. It held about 215 MiB more while the answer was
  sent. With two to four clients asking at once, the samples peaked at 725 to
  822 MiB. The server idled at 420 to 500 MiB. These are samples, not a bound.
- The node resets an answer that is still queued after 120 s. A 192 MiB answer
  needs at least 1.68 MB/s to finish in time.
- The memory savings were measured in harnesses, not on running nodes. The web
  node's saving was not measured in a browser.
- The
  [0.22.2 known issues](https://github.com/minanode/mina-rust/releases/tag/v0.22.2)
  still apply.
